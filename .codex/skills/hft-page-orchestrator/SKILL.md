# HFT 页面编排

在本项目中，页面生成默认走 HFT-SDK 接口文档，不支持脱离该文档的其他系统页面。

## 工作流

1. 先通过 `hft-sdk-contract` 在 `HFT-SDK-接口文档.md` 中检索页面对应的模块、接口、字段和事件。
2. 无论用户需求是否已经足够明确，都先做一次基于接口文档的二次确认，再进入页面生成。
3. 二次确认完成后，基于该契约直接生成首版可调用真实接口的页面。
4. 再使用 `reference-html` 统一 HFT 工作台风格，但样式不能覆盖接口约束。
5. 最后用 `html-artifact-delivery` 检查页面是否已经真实接通接口、真实渲染响应、真实处理状态，以及是否符合一屏展示规则。

## 核心规则

- 页面请求一律先做二次确认，再生成页面。
- 二次确认必须基于接口文档来问，不做脱离文档的泛化确认。
- 二次确认语气要友好、简洁、聚焦，让用户容易回答。
- 不要对用户说内部执行细节，例如“切到可写环境”“需要先落到项目文件”“权限不够所以先不改文件”之类的话术。
- 首次生成的页面就应直接调通真实接口，不要先给用户看静态页。
- 页面能力必须能在接口文档中检索到；检索不到就直接说明“当前系统不支持”。
- 字段不在接口文档中时，不要硬凑，不要猜；明确告知该字段未在接口文档中找到，并在页面中省略。

## 二次确认规则

只要用户请求页面，即使接口文档已经足够，也必须先和用户确认一次页面范围。

确认内容只围绕接口文档中可检索到的分歧点，不重复问已经没有歧义的内容。

优先确认：

- 页面具体是哪一个接口文档支持的页面或模块
- 同类能力下用户到底要哪一种场景
- 页面需要覆盖全部子场景，还是只做其中一种
- 是否需要 SSE
- 需要展示哪些文档中存在的字段

确认示例：

- 用户说“做个报单页面”时，应确认：
  是做全部报单能力，还是只做 FAK 报单，或只做双边报单等文档中已有场景。
- 用户说“做个行情页面”时，应确认：
  是内盘行情、做市行情、broker best quote、broker deal、market status，还是文档中其他已记录行情模块。

## 支持范围规则

- 默认仅支持从 `HFT-SDK-接口文档.md` 可检索内容生成页面。
- 用户请求的页面名、模块名、动作名、字段名，必须能在接口文档中找到依据。
- 如果页面名或页面能力找不到依据，应直接说明当前系统不支持该页面。
- 如果只是部分字段找不到依据，可以继续生成页面，但必须省略这些字段并明确告知用户。
- 不要把“接口文档里没有”解释成“可以先按理解生成”。

## 首版完成标准

首版页面同时满足以下条件后，才算完成：

- 已选中的主要操作都落成真实 `fetch` 调用，目标是文档中的接口。
- 页面主数据区由真实响应渲染，而不是本地静态数组。
- 如果契约要求实时订阅，页面中必须落成真实 `EventSource` 或等价订阅逻辑。
- 页面具备 loading、error、empty、success 等基础状态切换。
- 用户触发查询、提交、订阅后，页面会更新真实 DOM，而不是只改本地演示文本。
- 页面默认优先一屏展示；如果内容超出，应使用内部滚动区域，而不是让整页无限拉长。

## 生成前必须明确的事项

- 页面名称或模块名称
- 对应接口集合
- 关键动作
- 响应展示区域
- 需要展示的字段
- 不展示的字段清单
- 是否需要 SSE

## 最终输出约定

最终回答通常应包含：

1. 一次友好的二次确认
2. 用户确认后的简短摘要
3. 简要的 API / SSE 映射
4. 若有省略字段，列出“未在接口文档中找到，因此未展示”的字段清单
5. 一份首版即可真实调用接口、且默认一屏展示的完整 HTML 成品
