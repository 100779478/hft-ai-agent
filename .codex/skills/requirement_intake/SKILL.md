# Requirement Intake

## 目标

先把模糊需求补齐，再把结构化结果交给后续 skill。

## 必须收集的参数

- 页面名称
- 页面目标
- 目标用户
- 字段
- 操作
- 风格约束
- hft-sdk 接口约束

## 工作方式

1. 始终合并当前轮与之前轮次里已经确认的信息，不要只检查用户最新一条回复。
2. 用户即使不按标签格式回复，也要按语义提取并回填到七个参数里。
3. 如果用户一次性补齐了多个缺失项，必须按“累计上下文”重新判定，不允许把旧缺口逐项重复追问。
4. 只有在仍然缺少关键信息时才补问；一旦信息完整或可合理假设，立即流转到下一个 skill。

## 补问规则

1. 缺什么问什么，但只允许一次性列出当前全部缺失项。
2. 不要在连续多轮里每次只少问一项；必须给出完整缺失清单。
3. 对非关键细节优先使用合理默认值，并明确写入“默认假设”，不要为小问题反复打断用户。
4. 如果用户明确说“按默认”“你自行补齐”“参考当前项目约定”，就直接补默认，不再追问。

## 完成判定

满足以下任一条件即可视为完成：

- 七个参数都已明确提供
- 少量非关键项可由上下文或项目现状合理推断
- 用户授权使用默认值且默认值足以让后续 skill 执行

## 输出格式

补问未完成时，使用下面格式：

```text
[缺失项]
- 页面名称：...
- 字段：...
[/缺失项]

[回复模板]
页面名称：
页面目标：
目标用户：
字段：
操作：
风格约束：
hft-sdk 接口约束：
[/回复模板]
```

补问完成后，必须输出下面的结构化交接块，并停止继续追问：

```text
[INTAKE_COMPLETE]
页面名称：
页面目标：
目标用户：
字段：
操作：
风格约束：
hft-sdk 接口约束：
默认假设：
[/INTAKE_COMPLETE]
```
